# AI PR Review 助手产品需求文档 PRD

## 1. 项目背景

在软件开发团队中，Pull Request Review 是保障代码质量的重要环节。传统人工 Review 存在以下问题：

1. Review 成本高：开发者需要逐行阅读代码变更，耗费大量时间。
2. Review 不稳定：不同开发者经验不同，发现问题的能力不一致。
3. 上下文不足：Reviewer 可能不了解本次 PR 的完整背景和影响范围。
4. 重复性问题多：命名规范、空指针风险、异常处理、日志缺失、SQL 风险等问题经常重复出现。
5. 响应不及时：PR 提交后可能长时间无人 Review，影响开发效率。

因此，本项目设计并实现一个 AI PR Review 助手。用户指定 GitHub Pull Request 后，系统自动获取 PR 基本信息和代码变更，调用大模型进行智能分析，生成 PR 总结、风险代码识别和 Review 建议，辅助开发者提升 Review 效率与质量。

## 2. 项目目标

本项目目标是开发一个以 AI 辅助分析为核心的代码评审工具，帮助开发者快速理解 PR 变更内容，识别潜在风险，并生成可执行的 Review 建议。

核心目标包括：

1. 自动获取 GitHub PR 信息和代码 Diff。
2. 自动生成 PR 变更总结。
3. 自动识别风险代码，包括 Bug 风险、安全风险、性能风险、可维护性风险等。
4. 自动生成 Review 建议，帮助开发者修改代码。
5. 提供结构化 Review 报告，提升阅读体验。
6. 支持历史 Review 记录查询，便于追踪代码质量。
7. 在系统设计中考虑准确性、上下文理解、误报与漏报控制、响应速度和使用体验。

## 3. 目标用户

### 3.1 主要用户

1. 后端开发者
   希望快速理解 PR 变更，并发现潜在代码问题。
2. 前端开发者
   希望检查前端代码中的逻辑问题、接口调用问题和可维护性问题。
3. 项目负责人 / Tech Leader
   希望快速了解团队成员提交的 PR 质量和风险点。
4. 学生开发团队 / 比赛团队
   希望在协作开发中提高代码质量，减少低级错误。

### 3.2 使用场景

1. 开发者提交 PR 后，希望系统自动生成一份 Review 报告。
2. Reviewer 在人工 Review 前，先阅读 AI 总结，快速了解 PR 变更内容。
3. 团队希望发现潜在风险代码，如空指针、异常处理缺失、SQL 注入风险等。
4. 项目答辩或课程展示中，演示 AI 如何辅助软件工程协作。

## 4. 产品定位

AI PR Review 助手不是替代人工 Review，而是作为人工 Review 前的辅助工具。

它主要解决：

1. 帮助 Reviewer 快速理解 PR 变更。
2. 帮助发现常见风险和规范问题。
3. 帮助生成初步 Review 建议。
4. 帮助团队建立自动化代码质量检查流程。

它与直接把代码复制给 ChatGPT 的区别是：

1. 自动获取 GitHub PR，无需手动复制代码。
2. 自动解析 PR 文件、Diff 和提交信息。
3. 支持结构化输出 Review 报告。
4. 支持历史记录、任务状态和结果管理。
5. 支持后续扩展为 GitHub 评论、Webhook 自动触发和 CI/CD 集成。

## 5. MVP 功能范围

第一版 MVP 重点完成核心链路：

```text
输入 GitHub PR 链接
→ 获取 PR 信息
→ 获取 PR 变更文件
→ 解析 Diff
→ 调用大模型
→ 生成 Review 报告
→ 页面展示结果
→ 保存历史记录
```

### 5.1 MVP 必须实现功能

| 模块            | 功能                         | 说明                                   |
| --------------- | ---------------------------- | -------------------------------------- |
| PR 输入         | 输入 GitHub PR 链接          | 用户粘贴 GitHub PR URL                 |
| PR 解析         | 解析 owner、repo、pullNumber | 从 URL 中提取仓库和 PR 编号            |
| GitHub API 对接 | 获取 PR 信息                 | 获取标题、作者、描述、分支等           |
| GitHub API 对接 | 获取 changed files           | 获取变更文件列表和 patch               |
| Diff 解析       | 解析文件变更                 | 识别新增、修改、删除代码               |
| AI Review       | PR 总结                      | 总结本次 PR 做了什么                   |
| AI Review       | 风险代码识别                 | 识别潜在 Bug、安全、性能、可维护性问题 |
| AI Review       | Review 建议生成              | 给出修改建议                           |
| 报告展示        | 展示 Review 报告             | 展示总结、风险等级、建议列表           |
| 历史记录        | 保存 Review 任务             | 便于后续查看                           |
| 配置管理        | 模型 API 配置                | 配置模型供应商、API Key、模型名称      |

### 5.2 MVP 暂不实现功能

第一版不建议实现以下复杂功能：

1. GitHub OAuth 登录。
2. Webhook 自动触发。
3. 自动评论回 GitHub。
4. 多租户企业权限系统。
5. 复杂 Agent 工作流。
6. 代码仓库级 RAG。
7. 自定义规则引擎。
8. 多模型投票机制。
9. 完整 CI/CD 平台。

这些功能可以作为后续扩展方向。

## 6. 核心功能需求

## 6.1 创建 Review 任务

### 功能描述

用户输入 GitHub PR 链接，点击“开始评审”，系统创建 AI Review 任务。

### 输入

```json
{
  "prUrl": "https://github.com/example/demo/pull/12"
}
```

### 输出

```json
{
  "taskId": 10001,
  "status": "PENDING",
  "message": "Review 任务已创建"
}
```

### 业务规则

1. PR URL 必须符合 GitHub PR 链接格式。
2. 系统需要解析 owner、repo、pullNumber。
3. 如果仓库是 private，需要配置 GitHub Token。
4. 同一个 PR 可以多次发起 Review，但需要记录不同任务版本。

------

## 6.2 获取 PR 信息

### 功能描述

系统根据 PR 链接调用 GitHub API，获取 PR 基本信息。

### 需要获取的信息

1. PR 标题。
2. PR 作者。
3. PR 描述。
4. 源分支。
5. 目标分支。
6. 提交数量。
7. 变更文件数量。
8. 新增行数。
9. 删除行数。
10. PR 状态。

### 页面展示

在 Review 报告顶部展示：

```text
PR 标题：feat: add user login api
作者：zhangsan
源分支：feature/login
目标分支：main
变更文件：5 个
新增行数：120
删除行数：30
```

------

## 6.3 获取代码变更

### 功能描述

系统调用 GitHub API 获取 PR 中每个变更文件的 patch 内容。

### 需要保存的信息

1. 文件路径。
2. 文件状态：added、modified、removed、renamed。
3. 新增行数。
4. 删除行数。
5. patch 内容。
6. 文件语言类型。
7. 是否参与 AI Review。

### 过滤规则

为了控制响应速度和成本，以下文件可以默认跳过：

1. 图片文件。
2. 压缩包文件。
3. lock 文件，如 package-lock.json、yarn.lock。
4. 大型自动生成文件。
5. 超过指定大小的文件。

------

## 6.4 PR 变更总结

### 功能描述

AI 根据 PR 标题、描述、文件列表和代码变更，生成本次 PR 的整体总结。

### 输出内容

1. 本次 PR 主要做了什么。
2. 涉及哪些模块。
3. 主要代码变更点。
4. 是否可能影响已有功能。
5. 是否需要重点人工关注。

### 示例输出

```text
本次 PR 主要新增了用户登录接口，包括 LoginController、UserService 和 JWT 工具类相关改动。代码引入了 Token 生成逻辑，并新增了用户密码校验流程。需要重点关注密码加密方式、异常处理和 Token 过期时间配置。
```

------

## 6.5 风险代码识别

### 功能描述

AI 对代码 Diff 进行分析，识别潜在风险。

### 风险类型

| 风险类型         | 说明               |
| ---------------- | ------------------ |
| BUG_RISK         | 可能导致运行时错误 |
| SECURITY_RISK    | 可能导致安全问题   |
| PERFORMANCE_RISK | 可能导致性能问题   |
| MAINTAINABILITY  | 可维护性问题       |
| STYLE            | 代码规范问题       |
| TEST_RISK        | 测试不足           |
| COMPATIBILITY    | 兼容性风险         |

### 风险等级

| 等级   | 含义                     |
| ------ | ------------------------ |
| HIGH   | 高风险，建议必须修改     |
| MEDIUM | 中风险，建议优先修改     |
| LOW    | 低风险，可根据情况优化   |
| INFO   | 提示信息，不一定需要修改 |

### 每条风险建议包含

1. 文件路径。
2. 代码位置。
3. 风险类型。
4. 风险等级。
5. 问题描述。
6. 原因分析。
7. 修改建议。
8. 置信度。
9. 是否需要人工确认。

------

## 6.6 Review 建议生成

### 功能描述

AI 根据风险识别结果生成可执行 Review 建议。

### 建议要求

1. 建议必须具体，不要只说“优化代码”。
2. 建议必须说明原因。
3. 建议应尽量给出修改方向。
4. 不确定的问题要标记“需要人工确认”。
5. 不应对未出现在 Diff 中的代码做确定性判断。

### 示例

```text
文件：src/main/java/com/example/UserService.java
风险等级：HIGH
问题类型：SECURITY_RISK
问题描述：当前代码直接使用明文密码进行比较，存在安全风险。
修改建议：建议使用 BCryptPasswordEncoder 对密码进行哈希校验，避免明文密码存储或比较。
置信度：0.91
```

------

## 6.7 Review 报告展示

### 功能描述

前端展示 AI Review 结果。

### 页面内容

1. PR 基本信息卡片。
2. Review 任务状态。
3. PR 总结。
4. 风险统计。
5. 文件级 Review 结果。
6. 建议列表。
7. 每条建议的风险等级和置信度。
8. 复制 Review 建议按钮。
9. 重新评审按钮。

### 风险统计示例

```text

中风险：5
低风险：8
提示信息：3
```

### 功能描述

保存用户每次发起的 Review 任务，支持后续查看。

### 列表字段

1. 任务 ID。

7. 创建时间。
8. 完成时间。

## 7. 非功能需求

## 7.1 准确性

系统应通过以下方式提升准确性：

1. 将 PR 标题、描述、文件路径、Diff 内容一起提供给模型。
2. 对长 Diff 进行分块分析。
3. 使用结构化 Prompt 限制模型输出。
4. 要求模型只基于 Diff 内容判断，不确定时标记为“需要人工确认”。
5. 对文件级结果进行整体汇总，避免只看局部代码。

## 7.2 误报控制

系统应减少无效建议：

1. 要求模型输出置信度。
2. 对低置信度建议进行弱化展示。
3. 过滤泛泛而谈的建议。
4. 优先展示高风险和中风险问题。
5. 提示模型不要输出没有证据的问题。

## 7.3 漏报控制

系统应减少遗漏问题：

1. 按文件逐个分析。
2. 按风险类型检查：Bug、安全、性能、异常、并发、数据库、测试。
3. 对关键文件增加专项 Prompt。
4. 对整体 PR 进行二次汇总分析。

## 7.4 响应速度

系统应控制 Review 耗时：

1. 小 PR 同步处理。
2. 中大型 PR 使用异步任务。
3. 过滤无意义文件。
4. 对 Diff 分块并发调用模型。
5. 缓存已分析结果。

## 7.5 可用性

系统页面应简单易用：

1. 用户只需要输入 PR 链接即可开始。
2. Review 结果按照风险等级排序。
3. 支持复制单条建议。
4. 支持重新评审。
5. 错误信息需要明确提示。

## 7.6 安全性

系统需要注意：

1. GitHub Token 不允许明文展示。
2. API Key 不允许返回前端。
3. 敏感配置应加密存储或使用环境变量。
4. 日志中不打印完整 Token。
5. 对用户输入的 PR URL 做校验。

## 9. 任务状态设计

Review 任务状态包括：

| 状态         | 说明               |
| ------------ | ------------------ |
| PENDING      | 等待执行           |
| FETCHING_PR  | 正在获取 PR 信息   |
| PARSING_DIFF | 正在解析 Diff      |
| REVIEWING    | 正在调用 AI Review |
| SUMMARIZING  | 正在生成汇总报告   |
| SUCCESS      | Review 成功        |
| FAILED       | Review 失败        |
| CANCELLED    | 任务取消           |

## 10. 验收标准

MVP 版本完成后，应满足以下验收标准：

1. 用户可以输入 GitHub PR 链接创建 Review 任务。
2. 系统可以正确解析 owner、repo、pullNumber。
3. 系统可以获取 PR 基本信息。
4. 系统可以获取 PR 变更文件和 Diff。
5. 系统可以调用大模型生成 PR 总结。
6. 系统可以识别风险代码并生成 Review 建议。
7. 前端可以展示 Review 报告。
8. Review 结果可以保存到数据库。
9. 用户可以查看历史 Review 任务。
10. 系统对错误 PR 链接、无权限仓库、模型调用失败有明确提示。

## 11. 后续扩展方向

二期可以扩展：

1. GitHub OAuth 登录。
2. GitHub Webhook 自动触发 Review。
3. 自动将 Review 建议评论到 GitHub PR。
4. 支持 GitLab、Gitee。
5. 支持仓库级代码上下文检索。
6. 支持 RAG 检索相关文件、README、接口文档。
7. 支持多模型评审和结果投票。
8. 支持团队自定义 Review 规则。
9. 支持 CI/CD 集成。
10. 支持 Review 质量反馈闭环。
11. 支持生成单元测试建议。
12. 支持安全专项扫描。
13. 支持团队代码规范知识库。
