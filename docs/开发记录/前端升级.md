# AI PR Review 前端页面优化方案总结

## 一、前端优化目标

当前项目已经具备基础能力：

```
输入 PR 链接
→ 创建 AI Review 任务
→ 后端获取 PR Diff
→ 调用模型生成报告
→ 前端轮询任务状态
→ 展示评审结果
```

但当前页面更像一个“单功能 Demo 工具”，后续应升级为：

```
AI PR Review 工作台
+ 评审任务中心
+ 报告详情中心
+ 模型用量监控
+ Skill / Agent 扩展入口
```

最终目标是让项目看起来更像一个真实可用的 PR Review 平台，而不是简单的表单页面。

# 三、核心页面设计

## 1. Dashboard 工作台

Dashboard 是首页，也是演示时最重要的页面。

主要功能：

```
1. 输入 owner / repo 获取 Open PR 列表
2. 展示 GitHub PR 卡片
3. 点击 PR 后开始 AI Review
4. 展示最近评审任务
5. 展示配置状态
6. 展示简单统计数据
```

页面布局：

```
顶部：项目介绍 + 统计卡片
中间左侧：GitHub PR 列表
中间右侧：最近评审任务
底部：配置状态
```

PR 卡片展示：

```
PR 编号
PR 标题
作者
sourceBranch → targetBranch
更新时间
变更文件数
additions / deletions
开始评审按钮
打开 GitHub 按钮
```

如果后端支持缓存，点击“开始评审”时：

```
forceRefresh=false
→ 命中缓存：直接跳转历史报告
→ 未命中缓存：创建新任务并轮询
```

------

## 2. PR 列表页 Pull Requests

这是 Dashboard 中 PR 工作台的增强版。

主要功能：

```
1. 输入 owner / repo 获取 PR 列表
2. 支持 open / closed / all 筛选
3. 支持查看是否已有历史报告
4. 支持开始评审
5. 支持强制重新分析
6. 支持打开 GitHub 原页面
```

适合展示项目从“输入 PR 链接”升级为“选择 PR 工作流”。

------

## 3. 评审任务中心 Tasks

解决用户刷新页面后找不到报告的问题。

主要功能：

```
1. 查看历史 Review 任务
2. 按状态筛选
3. 按风险等级筛选
4. 按仓库或关键词搜索
5. 查看是否命中缓存
6. 查看失败原因
7. 点击进入报告详情
```

表格字段建议：

```
任务ID
PR标题
仓库
PR编号
状态
风险等级
风险分数
模型名称
Prompt版本
是否缓存
创建时间
操作
```

## 4. 报告详情页 Report Detail

路径：

```

```

顶部展示：

```
PR 标题
仓库
作者
sourceBranch → targetBranch
状态
风险等级
风险分数
模型名称
Prompt 版本
缓存状态
创建时间
```

按钮：

```

重新分析
复制 GitHub Review 评论

```

Tab 设计：

```
1. 总览
2. 文件视图
3. Review 建议
4. 模型用量
5. Skill 结果
6. 执行轨迹
```

### 总览 Tab

展示：

```
风险评分卡片
PR 信息卡
AI 总结
主要变更
最终建议
风险数量统计
```

### 文件视图 Tab

按文件展示评审结果：

```

语言
变更状态
additions / deletions / changes
AI 文件总结

```

这会让系统更像真正的代码评审工具。

### Review 建议 Tab

按风险等级筛选和展示：

```
HIGH
MEDIUM
LOW
INFO
```

每条建议展示：

```
riskType
riskLevel
title
description
reason
suggestion
line
confidence
needHumanCheck
```

### 执行轨迹 Tab

当前阶段展示固定 Pipeline：

```

解析 Diff

```

后续 Agent 化后，可以升级为：

```

Agent Final
```

# 六、与缓存机制的前端联动

后端新增数据库缓存后，前端需要支持：

```
cached=true
cachedFromTaskId
forceRefresh
```

默认点击“开始评审”：

```
{
  "prUrl": "...",
  "forceRefresh": false
}
```

如果命中缓存：

```
提示：已命中历史报告，直接展示
跳转 /tasks/{taskId}
不进行长时间轮询
```

如果用户点击“重新分析”：

```
{
  "prUrl": "...",
  "forceRefresh": true
}
```

页面显示：

```
本次为强制重新分析，不使用历史缓存。
```

# 七、与 Skill / Agent 的扩展关系

前端应提前预留两个区域：

```
Skill 结果 Tab
执行轨迹 Tab
```

当前版本：

```
展示固定 Pipeline
展示 Skill 空状态
```

后续版本：

```
Skill 结果 Tab 展示每个 Skill 的执行情况
执行轨迹 Tab 展示 Agent 的 Plan / Action / Observation / Final
```

这样后端从 Pipeline 升级到 Agent 时，前端结构不用推翻。

# 九、最终定位总结

前端最终不应该只是：

```
输入 PR 链接 → 展示报告
```

而应该升级为：

```
AI PR Review 工作台
```

核心能力包括：

```
找 PR
建任务
看历史
看报告
看文件维度建议
复制 GitHub 评论
监控模型用量
展示 Skill 结果
预留 Agent 执行轨迹
```

一句话总结：

**最终版前端要围绕“PR、任务、报告、文件、模型用量、Skill、执行轨迹”设计。这样当前能稳定演示，后续加缓存、Skill、Agent、Token 监控都不用推翻页面结构。**
