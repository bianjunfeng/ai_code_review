# AI PR Review 助手项目开发协作规范

## 1. 文档说明

本文档用于规范 AI PR Review 助手项目在两人协作开发过程中的开发方式、Git 使用、代码风格、接口设计、数据库设计、AI Prompt 编写、测试、部署、文档书写、安全管理和最终交付流程。

本项目开发周期较短，采用 AI 工具辅助软件设计与开发。为了避免两名成员在开发风格、代码结构、接口格式、文档风格和部署方式上的差异，特制定本规范。

本规范适用于项目全过程：

```text
需求分析
技术设计
编码开发
接口联调
AI Prompt 调试
测试验收
部署运行
文档整理
最终展示
```

------

# 2. 项目协作规范

## 2.1 协作原则

本项目采用两人协作开发方式，不采用单纯的前后端分工，而采用全阶段双闭环分工：

```text
成员 A：PR 获取与任务闭环负责人
成员 B：AI Review 与报告闭环负责人
```

两名成员均参与：

```text
需求分析
技术设计
功能开发
联调测试
文档整理
最终展示
```

## 2.2 成员 A 职责

成员 A 主要负责：

```text
PR URL 解析
GitHub API 对接
PR 基本信息获取
changed files / diff 获取
Review 任务创建
任务状态流转
任务与文件数据存储
任务查询接口
PR 获取相关异常处理
相关文档补充
```

## 2.3 成员 B 职责

成员 B 主要负责：

```text
Prompt 设计
AI Review 流程设计
大模型调用协作
AI 返回结果解析
风险类型和风险等级设计
Review 建议生成
Review 报告展示
误报漏报控制说明
相关文档补充
```

## 2.4 同步机制

开发期间建议每 2 小时同步一次。

每次同步需要确认：

```text
1. 当前完成了什么。
2. 是否有接口字段变化。
3. 是否有数据库字段变化。
4. 是否有阻塞问题。
5. 是否影响对方开发。
6. 是否影响最终演示。
```

## 2.5 接口变更规则

如果接口路径、请求参数或响应字段发生变化，必须同步通知另一名成员，并更新接口文档。

接口变更必须包含：

```text
接口路径
请求方法
请求参数
响应字段
字段含义
是否兼容旧版本
```

## 2.6 阻塞处理规则

如果某个任务超过 30 分钟无法推进，应及时说明问题，不要独自卡住。

常见阻塞包括：

```text
GitHub API 无权限
模型 API 调用失败
JSON 解析失败
数据库连接失败
前后端接口字段不一致
页面无法展示数据
```

处理方式：

```text
先记录错误信息
再截图或复制报错
然后同步给另一名成员
必要时先使用 mock 数据继续开发
```

# 3. Git 分支与提交规范

## 3.1 分支设计

本项目建议使用以下分支：

```text
main：最终稳定版本
dev：日常集成分支
feature/pr-task-chain：PR 获取与任务闭环分支
feature/ai-report-chain：AI Review 与报告闭环分支
```

## 3.2 分支使用规则

```text
1. main 分支只保留最终可运行版本。
2. dev 分支用于日常集成。
3. 每名成员在自己的 feature 分支上开发。
4. 不允许直接在 main 分支开发。
5. 合并到 main 前必须保证项目可以启动和演示。
```

## 3.3 推荐开发流程

```bash
git checkout dev
git pull origin dev
git checkout -b feature/pr-task-chain
```

开发完成后：

```bash
git add .
git commit -m "feat: add github pr preview api"
git push origin feature/pr-task-chain
```

合并前：

```bash
git checkout dev
git pull origin dev
git merge feature/pr-task-chain
```

## 3.4 Commit Message 规范

提交信息采用以下格式：

```text
类型: 简要说明
```

常用类型：

| 类型     | 含义                   |
| -------- | ---------------------- |
| feat     | 新增功能               |
| fix      | 修复问题               |
| docs     | 修改文档               |
| refactor | 重构代码               |
| test     | 增加或修改测试         |
| chore    | 配置、构建、依赖等杂项 |
| style    | 代码格式调整           |
| perf     | 性能优化               |

示例：

```text
feat: add github pr url parser
feat: add ai review prompt renderer
fix: handle github api unauthorized error
docs: update project development standard
chore: add gitignore config
```

## 3.5 禁止提交内容

禁止提交以下内容：

```text
API Key
GitHub Token
数据库密码
本地 IDE 配置
target/
node_modules/
.env
application-local.yml
临时测试文件
无用日志文件
```

# 4. 通用代码开发规范

## 4.1 命名规范

代码命名应清晰表达含义，避免使用无意义缩写。

推荐：

```text
ReviewTaskService
GitHubPullRequestService
AiReviewService
PromptRenderer
ReviewReportVO
```

不推荐：

```text
TestService
DoService
AService
TempController
DataUtil2
```

## 4.2 方法规范

方法应尽量只做一件事。

建议：

```text
单个方法不超过 80 行
复杂逻辑拆分为多个私有方法
避免在 Controller 中写大量业务逻辑
避免在 Service 中写大量重复代码
```

## 4.3 注释规范

以下情况需要写注释：

```text
复杂业务流程
状态流转逻辑
GitHub API 字段映射
AI Prompt 构造逻辑
JSON 兜底解析逻辑
安全相关逻辑
```

不需要为简单 getter、setter 或明显代码写无意义注释。

## 4.4 调试代码规范

开发时可以使用调试日志，但提交前必须清理：

```text
System.out.println
console.log
临时测试接口
无用 mock 数据
无用注释代码
```

如需保留日志，必须使用规范日志方式。

## 4.5 代码格式化

提交前应格式化代码。

要求：

```text
Java 代码缩进统一
Vue / JS 代码缩进统一
SQL 语句格式清晰
Markdown 标题层级清晰
```

# 5. 后端开发规范

## 5.1 后端目录结构

后端建议采用以下结构：

```text
backend/src/main/java/com/aipr/review
├── common
├── config
├── controller
├── service
│   ├── github
│   ├── review
│   ├── ai
│   ├── prompt
│   └── report
├── domain
├── dto
├── vo
├── mapper
└── enums
```

## 5.2 各目录职责

| 目录       | 职责                   |
| ---------- | ---------------------- |
| common     | 通用返回、异常、工具类 |
| config     | 配置类                 |
| controller | 接收 HTTP 请求         |
| service    | 业务逻辑               |
| domain     | 数据库实体             |
| dto        | 请求参数对象           |
| vo         | 响应结果对象           |
| mapper     | 数据库访问             |
| enums      | 枚举类                 |

## 5.3 Controller 规范

Controller 只负责：

```text
接收请求
参数校验
调用 Service
返回统一结果
```

不应在 Controller 中写：

```text
GitHub API 调用细节
数据库复杂逻辑
AI Prompt 拼接逻辑
JSON 解析逻辑
```

## 5.4 Service 规范

Service 负责业务逻辑。

例如：

```text
GitHubPullRequestService：负责 GitHub PR 获取
ReviewTaskService：负责任务创建和查询
AiReviewService：负责 AI Review 执行
ReviewReportService：负责报告聚合
```

## 5.5 DTO / VO / Entity 规范

```text
DTO：前端请求参数
VO：后端返回给前端的数据
Entity / Domain：数据库表映射对象
```

不建议直接把数据库 Entity 返回给前端。

## 5.6 统一返回格式

所有接口统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

失败示例：

```json
{
  "code": 40001,
  "message": "PR 链接格式错误",
  "data": null
}
```

## 5.7 异常处理

后端必须使用全局异常处理。

建议异常类型：

```text
BusinessException：业务异常
RuntimeException：系统异常
MethodArgumentNotValidException：参数校验异常
```

错误信息必须对用户友好，不要直接返回底层堆栈。

# 6. 前端开发规范

## 6.1 前端目录结构

```text
frontend/src
├── api
├── views
├── components
├── router
├── utils
└── assets
```

## 6.2 页面职责

| 页面                 | 职责                           |
| -------------------- | ------------------------------ |
| HomeView.vue         | 输入 PR 链接，创建 Review 任务 |
| ReviewTaskDetail.vue | 展示任务状态和 Review 报告     |
| HistoryView.vue      | 展示历史任务，可选             |

## 6.3 组件规范

通用展示内容应拆分为组件。

建议组件：

```text
RiskTag.vue
ReviewCommentCard.vue
TaskStatusTag.vue
PrInfoCard.vue
RiskOverviewCard.vue
```

## 6.4 API 请求规范

所有请求统一放到：

```text
frontend/src/api/
```

示例：

```js
import axios from 'axios'

const request = axios.create({
  baseURL: 'http://localhost:8080/api',
  timeout: 60000
})

export function createReviewTask(data) {
  return request.post('/review-tasks', data)
}

export function getReviewReport(taskId) {
  return request.get(`/review-tasks/${taskId}/report`)
}
```

页面中不直接写复杂 axios 配置。

## 6.5 页面状态规范

每个页面都需要处理：

```text
loading 状态
success 状态
error 状态
empty 状态
```

例如：

```text
AI 正在分析中，请稍候
暂无 Review 建议
任务执行失败，请检查 PR 链接或模型配置
```

## 6.6 错误提示规范

错误提示应明确、可理解。

推荐：

```text
PR 链接格式错误，请输入 GitHub Pull Request 地址
AI 分析失败，请稍后重试
GitHub 仓库无权限，请检查 Token 或仓库权限
```

不推荐：

```text
error
undefined
500
Network Error
```

# 7. 接口设计规范

## 7.1 REST API 命名

接口路径使用名词复数形式。

推荐：

```text
POST /api/review-tasks
GET /api/review-tasks/{taskId}
GET /api/review-tasks/{taskId}/files
GET /api/review-tasks/{taskId}/comments
GET /api/review-tasks/{taskId}/report
```

不推荐：

```text
POST /api/createTask
GET /api/getTask
POST /api/doReview
```

## 7.2 HTTP 方法规范

| 方法   | 用途           |
| ------ | -------------- |
| GET    | 查询           |
| POST   | 创建或执行操作 |
| PUT    | 全量更新       |
| PATCH  | 局部更新       |
| DELETE | 删除           |

## 7.3 请求参数规范

请求字段使用 camelCase。

示例：

```json
{
  "prUrl": "https://github.com/example/demo/pull/12"
}
```

## 7.4 响应字段规范

响应字段使用 camelCase。

示例：

```json
{
  "taskId": 1,
  "prTitle": "feat: add login api",
  "highCount": 1,
  "mediumCount": 2
}
```

## 7.5 时间格式规范

时间字段统一使用：

```text
yyyy-MM-dd HH:mm:ss
```

或 ISO 格式：

```text
2026-05-29T10:30:00
```

同一项目中应保持一致。

## 7.6 接口文档更新规则

新增或修改接口时，需要同步更新：

```text
docs/04-接口设计.md
README.md 中的核心接口部分
```

# 8. 数据库设计规范

## 8.1 表命名规范

数据库表名使用小写加下划线。

推荐：

```text
review_task
review_file
review_comment
model_config
prompt_template
```

## 8.2 字段命名规范

字段名使用小写加下划线。

推荐：

```text
task_id
file_path
risk_type
created_at
updated_at
```

## 8.3 主键规范

每张表统一使用：

```sql
id BIGINT PRIMARY KEY AUTO_INCREMENT
```

## 8.4 时间字段规范

每张核心表建议包含：

```sql
created_at DATETIME DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

如果是日志表或评论表，可以只保留 `created_at`。

## 8.5 状态字段规范

状态字段使用字符串，便于阅读和调试。

Review 任务状态：

```text
PENDING
FETCHING_PR
PARSING_DIFF
REVIEWING
SUMMARIZING
SUCCESS
FAILED
CANCELLED
```

## 8.6 索引规范

常用查询字段需要建立索引。

建议索引：

```text
review_task.status
review_task.created_at
review_task.owner + repo + pull_number
review_file.task_id
review_comment.task_id
review_comment.file_id
review_comment.severity
```

## 8.7 SQL 文件存放规范

SQL 脚本存放在：

```text
backend/src/main/resources/sql/
```

或：

```text
docs/sql/
```

建议文件命名：

```text
V1__init_schema.sql
V2__add_model_config.sql
```

# 9. AI 调用与 Prompt 规范

## 9.1 模型调用规范

前端不允许直接调用大模型 API。

所有模型调用必须通过后端统一入口：

```text
LlmClient
OpenAiCompatibleClient
```

## 9.2 模型配置规范

模型配置通过环境变量或配置文件读取：

```text
AI_BASE_URL
AI_API_KEY
AI_MODEL_NAME
AI_TEMPERATURE
```

禁止将 API Key 写死在代码中。

## 9.3 Prompt 存放规范

Prompt 文档统一存放：

```text
docs/05-Prompt设计.md
```

代码中的 Prompt 模板可以存放在：

```text
service/prompt/
```

或数据库表：

```text
prompt_template
```

## 9.4 Prompt 变量命名

Prompt 中变量使用双大括号：

```text
{{prTitle}}
{{prDescription}}
{{filePath}}
{{fileStatus}}
{{language}}
{{patch}}
```

## 9.5 模型输出规范

AI Review 输出必须尽量约束为 JSON。

文件级 Review 输出格式：

```json
{
  "filePath": "src/main/java/UserService.java",
  "summary": "该文件主要新增用户登录校验逻辑。",
  "comments": [
    {
      "line": null,
      "riskType": "SECURITY_RISK",
      "severity": "HIGH",
      "title": "密码明文比较存在安全风险",
      "description": "当前代码直接比较明文密码。",
      "suggestion": "建议使用 BCryptPasswordEncoder。",
      "confidence": 0.92,
      "needHumanCheck": true
    }
  ]
}
```

## 9.6 风险类型规范

统一使用以下风险类型：

```text
BUG_RISK
SECURITY_RISK
PERFORMANCE_RISK
MAINTAINABILITY
STYLE
TEST_RISK
COMPATIBILITY
```

## 9.7 风险等级规范

统一使用以下风险等级：

```text
HIGH
MEDIUM
LOW
INFO
```

## 9.8 误报控制规范

Prompt 中必须要求：

```text
只基于提供的 Diff 内容分析
不编造未提供的业务背景
不确定时 needHumanCheck=true
每条建议必须给出 confidence
不要输出泛泛而谈的建议
```

## 9.9 JSON 解析兜底规范

如果模型返回：

~~~text
```json
{...}
需要先去掉 Markdown 代码块标记，再解析 JSON。

如果解析失败：

```text
记录原始返回摘要
任务状态标记为 FAILED
返回“模型返回格式异常，请重新评审”
~~~

# 10. 测试规范

## 10.1 测试范围

项目至少需要测试以下内容：

```text
PR URL 解析
GitHub API 获取
Review 任务创建
AI 模型调用
AI JSON 解析
报告接口返回
前端页面展示
错误提示
```

## 10.2 正常场景测试

必须测试：

```text
输入正确 GitHub PR 链接
成功获取 PR 标题
成功获取 changed files
成功创建 Review 任务
成功调用 AI
成功展示 Review 报告
```

## 10.3 异常场景测试

必须测试：

```text
PR 链接格式错误
PR 不存在
GitHub Token 无效
private 仓库无权限
changed files 为空
模型 API Key 错误
模型调用超时
模型返回非 JSON
数据库连接失败
```

## 10.4 测试用 PR 规范

建议准备一个固定测试 PR，不要每次临时找。

测试 PR 中可以故意包含：

```text
明文密码比较
SQL 拼接
吞异常
缺少空指针判断
缺少日志
缺少测试
```

## 10.5 联调验收流程

每次大功能完成后按以下流程测试：

```text
1. 启动后端。
2. 启动前端。
3. 输入测试 PR 链接。
4. 创建 Review 任务。
5. 查看任务状态。
6. 等待 AI 分析完成。
7. 查看 Review 报告。
8. 检查数据库记录。
9. 刷新页面，确认报告仍可查看。
```

# 12. 日志与异常处理规范

## 12.1 日志级别

| 级别  | 使用场景               |
| ----- | ---------------------- |
| info  | 正常业务流程           |
| warn  | 可恢复异常或非关键问题 |
| error | 系统异常、外部服务失败 |

## 12.2 必须记录的日志

```text
任务创建
PR URL 解析结果
GitHub API 调用开始和结束
获取文件数量
模型调用开始和结束
模型返回解析结果
任务最终状态
异常原因
```

## 12.3 禁止记录的内容

日志中禁止打印：

```text
GitHub Token
AI API Key
数据库密码
完整密钥
用户敏感信息
```

## 12.4 异常返回规范

异常返回必须统一格式：

```json
{
  "code": 40001,
  "message": "PR 链接格式错误",
  "data": null
}
```

不要直接返回：

```text
NullPointerException
stack trace
SQL error 原始堆栈
```

```text
SSH 私钥
.env 文件
application-local.yml
```

```text
*.env
application-local.yml
target/
node_modules/
dist/
.idea/
.vscode/

```

```text

前端不直接调用模型 API
```

```text
只配置必要权限
不要使用个人主账号高权限 Token
不要把 Token 发给他人
Token 泄露后立即撤销
```

# 16. 演示与交付规范

## 16.1 演示前准备

演示前必须准备：

```text
稳定可用的测试 PR 链接
GitHub Token
AI API Key
数据库已初始化
后端服务可启动
前端页面可访问
备用截图
README 完整
```

## 16.2 演示流程

演示流程固定为：

```text
1. 打开系统首页。
2. 输入 GitHub PR 链接。
3. 点击开始评审。
4. 系统创建 Review 任务。
5. 展示 PR 基本信息。
6. 展示任务状态。
7. 等待 AI 分析完成。
8. 展示 AI 总结。
9. 展示风险统计。

11. 说明误报和漏报控制方式。
12. 说明未来扩展 Skill、RAG、Agent、Webhook。
```

演示前不建议：

```text
临时更换模型
临时更换 PR 链接
临时修改 Prompt
临时修改数据库
临时合并未测试代码
```

最终交付包括：

```text

frontend/
README.md
docs/
测试 PR 链接
演示说明
```

两天开发结束后，最低必须满足：

```text

3. 用户可以输入 GitHub PR 链接。
4. 系统可以获取 PR 信息和 diff。
5. 系统可以调用大模型。

8. README 和核心文档完整。
```

如果时间不足，可以暂缓：

```text
GitHub OAuth 登录
Webhook 自动触发
自动评论到 GitHub
完整 Skill 平台
RAG
Agent
多模型投票
复杂管理后台
```

# 18. 总结

本规范用于保证 AI PR Review 助手项目在短周期、两人协作、AI 工具辅助开发的情况下仍能保持统一的开发风格、接口格式、代码结构、文档风格和交付质量。

开发过程中应优先保证核心链路：

```text
输入 PR 链接
→ 获取 PR Diff
→ 调用 AI Review
→ 生成报告
→ 页面展示
```

所有规范都服务于最终目标：让项目在两天内完成一个可运行、可展示、可说明的 MVP 版本。
